## Protocol

`ai-dotnet/benchmarks/run-e5-matched.sh cpu|cuda <out> 3 6 10`: three rounds, each a fresh process of C# library, C# direct (ids path), Python, then 10 cold-start processes per language. Interleaving puts slow drift and foreign load on both languages. Warm: `max(10, requests)` warmup calls, then 200/100/30 (CPU) or 300/200/100 (CUDA) timed calls for short inputs at batch 1/8/32, 30/10/5 or 100/30/15 for 512-token inputs. `intra_op_num_threads=6` (physical cores), `inter_op_num_threads=1`, sequential execution, all graph optimizations; CUDA `use_tf32=0`, output copied to host inside every timed call (GPU synchronization included). Medians with 95% hierarchical bootstrap intervals (resample runs, then samples). p99 is not reported anywhere: no group reaches 1,000 samples.

What each side times: `ai-dotnet/benchmarks/README.md`, "What is timed". C# library is the product API (`E5Tokenizer` + `E5Encoder.EmbedBatch`); C# direct is a raw `InferenceSession` running the identical workflow; Python is `tokenizers` + NumPy + `InferenceSession.run`.

- **CPU:** no warm C#/Python difference is resolved at 95% in any of the 20 warm rows; every interval contains 1. Point estimates range from 0.92 to 1.11. The ORT run dominates (`run` stage 4.5 ms of 4.6–4.9 ms at short-b1); tokenization is 0.08 ms per short text in both languages, pre/post-processing below 0.15 ms.

Spawn to first embedding of one query text. Stage medians (CPU): C# spawn-to-Main 26 ms, **tokenizer load 1,332 ms**, session create 549 ms, first tokenize 34 ms, first encode 19 ms; Python spawn-to-script 21 ms, imports 111 ms, tokenizer load 538 ms, session create 446 ms, first request 6.5 ms. CUDA adds about 250 ms of session creation in both (C# 798 ms, Python 670 ms) and about 115–130 ms on the first run (CUDA kernel initialization).

The C# cold start is slower than Python's, and the gap is almost entirely `E5Tokenizer.FromFile` (parsing the 17 MB `tokenizer.json` and building the Unigram model in the owned tokenizer, including JIT): 1.33 s against 0.54 s for the Rust `tokenizers` library. The ORT session itself takes 100–130 ms longer in C#. This is a real, user-visible gap (plan 11: publish unfavorable results); see Decisions.

## Adapter overhead budget (plan 11): library against direct C#

Target: p95 overhead of the Starling layers no greater than the larger of 1 ms or 10% of direct execution. Verdict "met" when the upper end of the 95% interval of the p95 difference is within the budget, "not met" when the lower end exceeds it, otherwise "inconclusive".

- **CUDA:** met in 8 of 10 ids-path rows (short batches 1 and 8 at concurrency 1 and 4, short-b32, and long512 at batch 1, 8 and 32 with concurrency 1); inconclusive at long512-b1 and long512-b8 with concurrency 4 (wide intervals). At long512-b8 the library's p95 is 3.8 ms (0.2–4.8) above direct, within the 5.2 ms budget; its median is 0.2 ms above.
- **CPU:** met in 1 of 9 (long512-b32 has too few samples for p95), inconclusive in 8: the p95 intervals on this machine are wider than the budget (for example short-b1: +0.09 ms, interval −1.65 to +1.91, budget 1 ms). Medians agree within 1–2%. No row is "not met". CPU p95 cannot be resolved to 1 ms without a quieter machine or many more samples.

So the budget is met on CUDA and not yet demonstrated on CPU; nothing indicates it is exceeded.

## Load: not a controlled machine

- The RTX 3090 (GPU 0) runs the user's ComfyUI and was never used (0% utilization throughout). The RTX 4060 Ti holds another resident process (`strata`, about 9.8 GB of 16 GB) that was idle during the runs.
- Runs started after a quiet check (1-minute load below 3, GPU 1 below 10%, no process above 60% CPU, no test runs). A background log sampled every 5 s: during the CPU run (21:03–21:36 UTC) processes other than the benchmark used a median 36% of one core, but more than one full core in 28% of samples (peaks of 5 cores), mostly Chrome renderers and a local ClickHouse server; the user's desktop was in use. During the CUDA run (21:36–21:43 UTC) foreign CPU use was 0% median, above one core in 6% of samples. GPU 1 utilization outside the benchmark reached 37% once during the CPU run.
- This foreign load is the likely cause of the wide CPU p95 intervals. Interleaving puts it on both languages; it does not make CPU p95 differences resolvable.
- Two earlier CPU attempts the same afternoon (one without the load log, one whose load sampler stopped early) gave the same medians within a few percent and the same cold-start gap; they are superseded by this run and not summarized.

## Not done

- No controlled hardware, no fixed clocks; no Windows, macOS or ARM64 runs.
- VRAM, native memory, GC pauses and allocations per request are not recorded by the workload harness (allocations come only from the micro-benchmarks).
- No latency-bound concurrency sweep beyond 1 and 4; batch 32 only at concurrency 1.
- Text path cold start only; no acquisition time or package-size measurement (plan 11 "Setup").
- p99 is not reported (fewer than 1,000 samples per group).
