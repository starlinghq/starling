# Five-model onboarding workflow

Status (2026-10-18): the five profiles are on `main`, Experimental and source only (not published to nuget.org; `docs/releases/ai-0.2.0.md`, "Not published"). The three BERT profiles are in `Starlings.Models.Bert` (with recipes `minilm-cpu`, `bge-small-cpu` and `ms-marco-cpu` under `model-pipeline/recipes/`); #120 later parameterized the BERT route and admitted a sixth candidate, `nomic-ai/nomic-embed-text-v1.5` (`nomic-embed-cpu`), and #121 a seventh, `BAAI/bge-base-en-v1.5` (`bge-base-cpu`). The two Qwen profiles are in `Starlings.Models.QwenChat` (`qwen3-cpu`, `qwen25-cpu`). None has a registry profile.

## Objective and selection

Exercise the merged onboarding engine against five additional popular, open model profiles, delivering real CPU reference, backend, owned .NET, evaluation, resume, failure, and clean-consumer evidence. Work is isolated in `codex/five-model-onboarding`; EmbeddingGemma 2 and other active worktrees are excluded.

“Top” means widely used representatives selected for demand, architecture coverage, open access, and practical local testability, rather than the five largest or highest benchmark scores. The provisional portfolio is Qwen/Qwen3-0.6B, Qwen/Qwen2.5-0.5B-Instruct, sentence-transformers/all-MiniLM-L6-v2, BAAI/bge-small-en-v1.5, and cross-encoder/ms-marco-MiniLM-L6-v2. Record the selection date, Hub download counts, immutable revisions, licenses, and source links. Two Qwen generations exercise different attention/configuration and chat-template behavior; the BERT profiles exercise mean pooling, CLS pooling, and paired-input scoring. CPU fp32 is the initial execution profile. No GPU or paid service is required.

## Work units and ownership

1. **Admission and shared workflow (primary agent).** Pin each original snapshot and graph/builder, verify file sizes and SHA-256, write strict candidate contracts and recipes, and add a five-model workflow command with isolated per-model records. The workflow preserves failures, continues independent models, resumes verified stages, and exits unsuccessfully if any required model fails. Keep user machine bindings separate from portable recipes. Extend plugin dispatch while preserving the E5 recipe and its protected evaluator.
2. **Owned BERT tokenizer (smaller agent).** Implement the exact WordPiece, BertNormalizer, BertPreTokenizer, and WordPiece decoder combinations observed in the three pinned encoder snapshots. Reuse TemplateProcessing and pair/type-ID behavior. Validate parameter support; compare against pinned upstream tokenizers across Unicode, accents, CJK, controls, special tokens, truncation, padding, pairs, decode cleanup, and the maximum-word-length boundary. Production code retains no foreign tokenizer dependency. Update inspection to report precisely the implemented combinations.
3. **Embedding and reranking paths (workhorse agent).** Reuse the ONNX session infrastructure in new model-neutral BERT execution code with explicit contracts: MiniLM masked mean/L2/max256, BGE CLS/L2/max512 and explicit query instruction, and cross-encoder paired-input scalar scoring. Implement public typed APIs, owned tokenization, bounded batching/threading, model identity, errors, disposal, and a fidelity tool. Add reference and Python ORT stages with intermediate tensors and independent output checks. Do not disguise these models as E5.
4. **Generation paths (workhorse agent).** Reuse the isolated GenAI runtime for Qwen2.5 and Qwen3 CPU fp32. Build pinned bundles from verified original snapshots in temporary workspaces. Implement explicit text-only templates, validated tokenizer identity, a typed wrapper, and a fidelity tool. Compare original transformers, Python GenAI, and .NET paths; cover prompt rendering/IDs, initial logits, greedy IDs, EOS/stops/max tokens, stream reconstruction, usage, cancellation, cache behavior, and request isolation. Unsupported tools/multimodal input remains explicit. Do not reuse Qwen3.5 special IDs or its template contract.
5. **Development evaluation contracts (each task owner, primary review).** Fix candidate policies before executing models. Fresh references remain proposed artifacts; never write protected fixtures or tolerance files. Candidate parity reports are development evidence and explicitly leave protected release qualification unapproved. Evaluators reject missing/duplicate rows, wrong identities/shapes, non-finite data, and incomplete required evidence. Existing protected Qwen3.5/E5 fixtures may validate evaluator behavior without alteration. Independent fixture adoption is a separate reviewable change.
6. **Packaging and integration (primary with owners).** Restore and commit central dependency locks for new projects. Build packages from committed source and run clean external consumers offline with isolated caches and real models. Verify tokenizer independence and model/native identities. Provide a sample invocation for each task and retain small evidence in Git; weights and large tensors stay in ignored artifacts.
7. **Real-model acceptance and review (primary, independent agent).** Execute all five through the workflow, verify unchanged resume, invalidate one model’s evidence and show other models remain reusable, exercise an asset mismatch and a complete-evidence evaluator rejection, and export verified bundles. Run applicable Python/.NET/format/schema/dependency checks. Review semantics, cache declarations, source/output guards, and claims. Open draft PR(s) with exact results, limitations, and passing CI. Do not merge or release.

## Parallel boundaries

The primary agent owns recipe schema/loader plugin dispatch, CLI/workflow, candidate contracts and asset locks, common helper module, documentation/evidence, solution inclusion, and final integration. The tokenizer agent owns tokenizer components/loader, its tests, and capability inspection changes (coordinate recipe-loader edits with primary). The BERT agent owns its new model package/tool, plugin, reference runners, and tests. The generation agent owns its new model package/tool, plugin, reference/bundle runners, and tests. Agents do not commit/push, edit protected evidence, change CI permissions/secrets, or run concurrent expensive model inference. Root coordinates real workloads and source commits.

Use the existing `Stage(name, dependencies, inputs, parameters, execute)` interface and `describe_plan`/`build_stages` plugin entry points. Each stage declares relevant code, environment, original inputs, contract/policy, and dependency evidence. Avoid a blanket HEAD identity for expensive inference; committed candidate identity belongs in distribution/review stages. Every plugin must support the existing timeout/thread controls and safe output roots.

## Acceptance and limitations

- Exactly five selected models have runnable recipes and typed .NET inference paths with explicit experimental capability descriptors.
- One repeatable workflow executes every model against real pinned weights and produces honest per-model task parity and overall status.
- Discrete checks are exact; continuous checks use predefined policies and retain intermediate diagnostic evidence. Failure never becomes a supported status.
- Cached resume verifies complete output trees; cross-model isolation is demonstrated through corruption and repair.
- At least one clean-consumer real-model run per model executes without the repository or a Python production runtime.
- Existing E5 and Qwen3.5 paths and the separately developed EmbeddingGemma branch remain compatible.
- No protected fixtures/tolerances, credentials, weights, foreign production tokenizer dependency, or unrelated user files are changed.
- New candidate references/policies require independent maintainer adoption before protected G1/G2 release qualification. Passing development parity is not full release approval or a controlled performance claim.
- CPU execution is bounded to two threads per expensive run; model runs are sequential unless resource measurements justify bounded concurrency. Stop a repeated failure after two unsuccessful repair attempts and retain its minimal reproducer.
