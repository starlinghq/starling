# ai-dotnet release 0.4.0

**Starlings.Models.Bert reaches nuget.org.** This release follows `0.3.0` (published 2026-10-19) and carries the work merged since (#128 to #263). It adds ten packages to the publishable set. `Starlings.Models.Bert` carries the BERT route's seven embedding and reranking profiles, now including the multilingual `BAAI/bge-m3` embedder (#128) and the `BAAI/bge-reranker-v2-m3` cross-encoder reranker (#146, closes #99). All seven profiles are **Experimental**. The package now carries its profiles: `BertModelProfile.BuiltIn(name)` works from the package alone, with no repository checkout. The browser packages `Starlings.Runtime.OnnxWeb`, `Starlings.Runtime.OnnxWeb.WebGpu` and `Starlings.Models.E5.Browser` (#149, #150) run multilingual-e5-small in .NET browser-wasm apps on onnxruntime-web; their four profiles are **Experimental**. `Starlings.Models.Abstractions` (shared model contracts) is new, and the generation packages are split into model definitions without a runtime and their ONNX Runtime packages: `Starlings.Generation.Abstractions`, `Starlings.Models.Qwen35.OnnxGenAI`, `Starlings.Models.Kev.Onnx` and `Starlings.Models.QwenChat.OnnxGenAI` are new, and **the split is breaking** for 0.3.0 users of `Starlings.Models.Qwen35`, `Starlings.Models.QwenChat` and `Starlings.Models.Kev` (see [Upgrading from 0.3.0](#upgrading-from-030)). `Starlings.Models.Lfm3` (#217, #218, #220) runs `LiquidAI/LFM3-1.7B` text generation on ONNX Runtime; its profile is **Experimental**, and **its model license is the LFM Open License v1.0, not MIT or Apache-2.0: commercial use is licensed only to an entity below USD 10 million annual revenue** (see [LFM3](#new-package-starlingsmodelslfm3-lfm3-17b-experimental-217)).

**Publishing.** The `release` workflow publishes this release from the tag `ai-v0.4.0` on `main`, after a maintainer approves the `release` environment. It publishes the 27 packages of the publishable set below through NuGet trusted publishing, and creates a GitHub release with this record as notes.

**Tokenizer.** Every package that tokenizes now pins `Starlings.Tokenizers [0.3.4]` (0.3.0 in the previous release). #128 raised the pin to 0.3.1, which adds the lstrip/rstrip added-token options bge-m3 needs. #135 raised it to 0.3.2, which adds ByteLevel `use_regex` for Whisper. The move to 0.3.4 brings 0.3.3's `Sequence` post-processor, the Llama 3 split regex and the profiles `lfm3-bpe-chat`, `qwen3-bpe-embedding` and `qwen3-bpe-chat`, and 0.3.4's profile `clover-bpe-chat`. LFM3 needs `lfm3-bpe-chat`. No pinned asset of an existing profile declares any of these options, so their outputs are unchanged, and the tokenizer's conformance fixtures pass unchanged (starlinghq/tokenizers CHANGELOG). Every manifest's `processing.tokenizer.version` moved with the pin.

**Maturity.** Maturity belongs to profiles, not packages, and each package README has a generated maturity table. Every Stable profile of 0.3.0 is still Stable with the same contract: no gate, tolerance or `protected/` file changed. The new profiles are Experimental: no gate has run on them, and their capabilities are at most Experimental. They get registry manifests in this release candidate so the package README can state their maturity. Each manifest has every gate `not-run`. Their tolerances are the candidate's predeclared development policy (`qualification.tolerances` points at the candidate `profile.json`, as for QwenChat). Their references are proposed and not adopted into `protected/`. The BERT route has no admission record. The models were admitted to the onboarding route in the PRs below.

## Changes merged since #155

Everything below was merged to `main` after the release candidate opened and is part of 0.4.0 (moved here from `docs/releases/unreleased.md`).

### Build-time native package checks, CUDA recipe, Native AOT smoke check (backlog E1)

**Native package checks (new, in the packages).** `Starlings.Runtime.Onnx` and `Starlings.Generation.OnnxGenAI` pack MSBuild targets in `buildTransitive/`, so every executable or test project that consumes them, directly or through a model package, checks its restored package graph:

| Code | Level | Condition |
| --- | --- | --- |
| `STARLINGS001` | warning | `Starlings.Runtime.Onnx` without an ONNX Runtime native package |
| `STARLINGS002` | error | `Microsoft.ML.OnnxRuntime` and a `Microsoft.ML.OnnxRuntime.Gpu*` package together |
| `STARLINGS003` | warning | `Starlings.Generation.OnnxGenAI` without a GenAI native package |
| `STARLINGS004` | error | `Microsoft.ML.OnnxRuntimeGenAI` and `Microsoft.ML.OnnxRuntimeGenAI.Cuda` together |

Class libraries and browser projects are not checked. Opt-out properties: `StarlingsOnnxRuntimeNativeCheck`, `StarlingsOnnxRuntimeGenAINativeCheck`. No dependency of any package changed: the libraries still reference only the managed bindings, and no native package is referenced under `ai-dotnet/src/`.

**Guide.** [docs/guides/native-runtimes-and-cuda.md](../guides/native-runtimes-and-cuda.md): the native packages per runtime, the checks, the `-p:UseCuda=true` build recipe (one project, a CUDA lock file), Linux-only GPU dependencies (the CUDA libraries are the machine's; prefer `Microsoft.ML.OnnxRuntime.Gpu.Linux`; publish with a runtime identifier when `Microsoft.ML.OnnxRuntimeGenAI.Cuda` brings the Windows GPU natives) and the Native AOT status per package.

**Native AOT smoke check (tooling, not packed).** `tools/aot-smoke-ai.sh` publishes a consumer per package (`tools/release-drill/aot-smoke`) with `-p:PublishAot=true`, the whole package assembly rooted, no model files, and records which packages are AOT-clean. The release drill runs it with `--aot` or `--aot-smoke`. Run record: [docs/evidence/aot-smoke/](../evidence/aot-smoke/README.md).

**Release drill.** Checks that both packages carry their `buildTransitive` targets, that no sample or checker triggers a native package check, and builds four throwaway consumers (`tools/release-drill/native-check`) that must trigger `STARLINGS001` to `STARLINGS004`; the two-native cases restore the GPU packages (about 420 MB) into the drill's isolated cache.

**Not provided.** Runtime convenience packages (`Starlings.Runtime.Cpu`, `.Cuda`, GenAI equivalents) and per-family umbrella packages: CI forbids native package references under `ai-dotnet/src/`, and the checks above cover the failure they would prevent (see the guide).

### Onboarding: one BERT contract table, scaffold, route suggestions (backlog E2)

**`Starlings.Models.Bert`.** The per-repository contract table is no longer a hand-written `switch`: the package embeds `model-pipeline/routes/bert-onnx-cpu-v1/contracts.json`, the file the Python allow-list (`onboarding_bert.py`) reads, and validates it on first use with the same rules. New: `BertModelProfile.SupportedRepositories`. The seven contracts are unchanged value for value, and `Parse` accepts and rejects the same documents as before.

**model-pipeline.** `model-pipeline scaffold <candidate> [--write]` generates a BERT-route candidate's recipe, contract table entry, `tools/fetch-tokenizer-assets.sh` line, package README row, .NET contract-test row and a C# runtime lock. `model-pipeline inspect` now suggests `bert-onnx-cpu-v1` (with the observed task, pooling and normalization) or `qwen-genai-cpu-v1` as well as `e5-onnx-cpu-v1`. `model-pipeline/Dockerfile` describes a contributor image with the hash-locked reference environments; no CI job builds it and it is untested.

**Capability statuses.** None changed. No profile's contract, gate, tolerance or `protected/` file changed.

### Starlings.Models.Abstractions and the encoder de-duplication (backlog A2, D3)

**New package `Starlings.Models.Abstractions`** (references only `Starlings.Acquisition`; no ONNX Runtime). `Starlings.Models.E5`, `Starlings.Models.EmbeddingGemma2`, `Starlings.Models.Gliner2` and `Starlings.Models.Bert` reference it. Its types, all additive:

- `CapabilityStatus`: one status enum for every package.
- `ModelProfileCapabilities` (with `ProfileMaturity`, `TruncationPolicy`, `ProfilePlatform`): the machine-readable capability record of a profile, generated from its registry manifest by `model-pipeline catalog` into each package's `ProfileCapabilities.g.cs`. Contract fields: profile id, maturity, max input tokens, truncation policy, dimension, qualified providers. Informational: tasks, platform rows, stop token ids, the manifest's capabilities map. `docs/catalog/catalog.json` gains the same `behavior` fields and `qualified_providers` per profile. `model-pipeline catalog --check` (CI) fails when a generated file is stale, and each package's contract tests compare every record with its manifest field for field.
- `ITextEmbedder`: implemented by `E5TextEmbedder`, `EmbeddingGemma2TextEmbedder` (new overload `EmbedBatch(texts, tokenCounts, cancellationToken)` with no prompt; new `Dimension` and `MaxSequenceLength`) and `BertTextEmbedder` (new overload with the prompt `none`; new `MaxSequenceLength`). `E5TextEmbedder` gains `Dimension` and `MaxSequenceLength`.
- `IReranker`: implemented by `BertReranker` (new `Score(query, documents, cancellationToken)`, the raw logits of `ScoreBatch`).
- `IModelAssets<TFiles>`: `E5ModelAssets.Assets`, `EmbeddingGemma2ModelAssets.Assets` and `Gliner2ModelAssets.Assets` expose the static lock and acquisition members as an instance.
- `InputTooLongException` (an `ArgumentException` with `InputIndex`, `TokenCount`, `MaxTokens`): now the base of `EmbeddingGemma2InputTooLongException` and `Gliner2InputTooLongException`. `E5Encoder` throws it (instead of a plain `ArgumentException`, same message) for an id sequence above `MaxSequenceLength`.

**New members on the capability classes.** `E5Capabilities`, `EmbeddingGemma2Capabilities` and `Gliner2Capabilities` gain `Statuses` (the package-wide table in the shared enum) and `ProfileCapabilities` (the generated record of every profile the package serves, Stable or not).

**Obsolete, removed in the next minor version.** Each still works and returns the same values as before:

| Obsolete member | Replacement |
| --- | --- |
| `Starlings.Models.E5.CapabilityStatus`, `EmbeddingGemma2CapabilityStatus`, `Gliner2CapabilityStatus` | `Starlings.Models.CapabilityStatus` (same names and order) |
| `E5Capabilities.All`, `EmbeddingGemma2Capabilities.All`, `Gliner2Capabilities.All` | `XCapabilities.Statuses` |
| `E5Capabilities.Profiles`, `EmbeddingGemma2Capabilities.Profiles`, `Gliner2Capabilities.Profiles` | `XCapabilities.ProfileCapabilities[profile].Capabilities` |
| `EmbeddingGemma2InputTooLongException.MaximumTokens` | `MaxTokens` (the shared name; GLiNER2 already used it) |

**Encoder de-duplication, outputs unchanged.** Right-padded packing, mean and CLS pooling with L2 normalization (including the Matryoshka truncation) and the chunk run moved into one internal `EncoderCore` in `Starlings.Runtime.Onnx`, used by `E5Encoder`, `EmbeddingGemma2Encoder` (text and the multimodal text path) and the BERT route. The arithmetic and its order are unchanged. On CPU, embeddings and reranker scores from the moved code are bit for bit those of the code it replaces for e5, EmbeddingGemma 2 (768 and 128 dimensions, prompts, token budget with length sorting) and four BERT-route profiles (mean pooling, CLS pooling, an unnormalized embedder and a reranker). The tolerance-based CPU parity tests of these packages, the EmbeddingGemma 2 image tests included, pass before and after. The ML.NET transform internals (data view, cursors, bindings, row mapper) and the request and result handling of the two text `IEmbeddingGenerator`s are shared source now instead of two copies; public types and behavior are unchanged.

**Capability statuses.** None changed. No Stable profile's contract, gate, tolerance or `protected/` file changed.

### Token counting, chunking, streaming embeddings and an execution scheduler (backlog C2 to C5)

All additive and experimental; no Stable profile's contract, capability status, gate, tolerance or `protected/` file changed.

- **Token counting (C3).** `ITextEmbedder` gains `CountTokens(text)`, `CountTokens(texts)` and `Validate(text)`, implemented by `E5TextEmbedder`, `EmbeddingGemma2TextEmbedder` (with prompt overloads) and `BertTextEmbedder`. Counts include special tokens and are taken before truncation. `Validate` returns the new `TokenLimitCheck` (`TokenCount`, `MaxTokens`, `ExceedsLimit`, `TokenCountIsLowerBound`) and never throws. Capability `token_counting` (e5, EmbeddingGemma 2) and `BertCapabilities.TokenCounting`: experimental.
- **Chunking (C2).** `TextChunker` in `Starlings.Models.Abstractions`: sliding windows of tokens with overlap and a prefix budget over a model's tokenizer (`IChunkingTokenizer`, implemented by `E5Tokenizer`, `EmbeddingGemma2Tokenizer` and `BertTextEmbedder.ChunkingTokenizer`), returning chunk offsets, text and token counts; `EmbedPooled` returns the re-normalized mean of the normalized chunk vectors. Pooled vectors are not the reference model's output and carry no parity claim. Capability `chunking`: experimental.
- **EmbeddingGemma 2 rejects certainly-too-long text without tokenizing it (C2).** `EmbeddingGemma2Tokenizer` computes the longest token of its `tokenizer.json` at load (31 UTF-16 code units for the pinned file, `MaxCharactersPerToken`). The text embedder, the text generator (its micro-batching path included) and the new `EmbeddingGemma2Tokenizer.Tokenize(text, maxTokens)` reject text above `(limit - 2) * 31` code units (253,890 at the default 8,192 tokens) before tokenizing it, with `EmbeddingGemma2InputTooLongException` whose `TokenCount` is that lower bound and whose new `TokenCountIsLowerBound` (on `InputTooLongException`) is true. Shorter text is checked exactly, as before; embeddings are unchanged.
- **Streaming (C4).** `EmbedStreamAsync(IAsyncEnumerable<string>, options, cancellationToken)` on `E5EmbeddingGenerator` and `EmbeddingGemma2EmbeddingGenerator`: values are tokenized as they arrive and grouped exactly as the encoder groups an explicit batch, so with `SortByLength` off the embeddings equal one `GenerateAsync` call bit for bit. New capability `extensions_ai.stream`: experimental. The profile capability `streaming` stays unsupported on every profile.
- **Execution scheduler (C5).** `ExecutionScheduler` (`TaskScheduler?`) on `E5EmbeddingGeneratorOptions`, `EmbeddingGemma2EmbeddingGeneratorOptions`, `EmbeddingGemma2MultimodalEmbeddingGeneratorOptions` and `Gliner2ExtractorOptions`. Null (default) keeps today's inline behavior; a scheduler runs `GenerateAsync`, the stream's encoder runs and `ExtractAsync` as tasks on it. Every async member documents the contract: inline unless a scheduler is set. New capabilities `extensions_ai.execution_scheduler` (e5, EmbeddingGemma 2) and `execution_scheduler` (GLiNER2): experimental.

### Kev API items and one read of each graph at session creation (backlog B9 API items, C7)

All additive. No Stable profile's contract, capability status, gate, tolerance or `protected/` file changed; the Kev profiles stay Experimental and keep every existing capability status.

- **Branch budget (B9).** `KevOptions.MaxBranchTokens` (null by default): a limit on one question's branch alone, the state not counted. A longer branch is over the limit like an over-long row.
- **Every over-long question in one pass (B9).** The encoder checks every question before it throws: `KevInputTooLongException` gains `Limit` (`KevTokenLimit.State`, `Row` or `Branch`) and `OverLongQuestions` (each `KevOverLongQuestion` with `Index`, `Id`, `Limit`, `TokenCount`, `MaxTokens`); `QuestionIndex` is the first of them. With the new `KevOptions.DeclineOverLongQuestions = true`, `Decide` answers the other questions and lists the over-long ones in the new `KevDecision.Declined` (and `KevEncoding.Declined`, with `KevEncoding.QuestionIndices` mapping rows to questions); the answered questions' probabilities equal those of a request without the declined ones, bit for bit on CPU. A state over the limit still throws. Capabilities `branch_token_limit` and `decline_over_long_questions`: experimental.
- **Placement (B9).** `KevDecisionModel.Placement` returns a `KevPlacement`: provider, CUDA device, profile id, whether native calls are serialized, the session's captured node placement (`OnnxSessionOptions.CapturePlacement`) and `StateCacheInHostMemory` (true for the qualified bundles). Capability `placement_report`: experimental.
- **Calibration flag (B9).** `KevDecisionModel.IsCalibrated`, `KevAnswer.IsCalibrated` and `KevAnswer.Temperature`: true when the temperature in effect is the checkpoint's (`KevOptions.Temperature` null or set to that value). Capability `calibration_flag`: experimental.

### Acquisition surface: status, cleanup, progress, waits, concurrent files, mirrors, pruning, lock format 3 (backlog D1)

All additive in `Starlings.Acquisition`; defaults keep the former behavior. No Stable profile's contract, capability status, gate, tolerance or `protected/` file changed, and no model package's lock changed. Every new member is experimental, tested against the in-process fake Hub on Linux x64; no real-Hub, Windows or macOS run.

- **Status without exceptions.** `ModelAssetStore.Check(lock[, verification])` and `ModelAssetStore.CheckDirectory(lock, directory, verification)` return a `ModelAssetStatus`: `State` (`ModelAssetState`: `Complete`, `Missing`, `Incomplete`, `Invalid`), `SnapshotDirectory`, `MissingPaths`, `Problems` (`ModelAssetProblem` with `ModelAssetProblemKind` `SizeMismatch`, `DigestMismatch` or `Unreadable`, expected and actual size and digest, and the message `OpenLocal` would throw), `MissingBytes` and `Snapshot` when complete. `TryOpenLocal(lock[, verification], out snapshot)` returns false instead of throwing.
- **Verification per call.** `OpenLocal(lock, verification)`, and `DownloadAsync(lock, ModelDownloadOptions, cancellationToken)` whose `ModelDownloadOptions` carries `Verification`, `Progress`, `LockWaitTimeout` and `MaxConcurrentFiles` (null members use the store's options). A store is thread-safe and can be kept for the process instead of being built per call.
- **Lock totals in progress.** `ModelAssetProgress` gains `FileIndex`, `FileCount`, `LockBytesProcessed` and `LockTotalBytes`; values are reported one at a time, also with concurrent files. New stage `ModelAssetStage.Waiting`, reported once while another downloader holds a file's lock.

- **Concurrent files.** `ModelAcquisitionOptions.MaxConcurrentFiles` (default 1: one file after the other in lock order, as before).
- **Mirrors and offline sources.** `ModelAcquisitionOptions.FallbackEndpoints`: Hub-layout http or https addresses (another scheme is rejected when the store is created) tried in order after `Endpoint`, for files without an explicit source, after a download failure, 401/403, 404 or bytes that do not match. A mirror receives the token only under the existing rule (https, and the host of `Endpoint` or `huggingface.co`). When every address fails, the `Endpoint` failure is thrown and the new `ModelAcquisitionException.EndpointFailures` lists all of them. `LocalSources`: directories laid out like the cache, copied from with size and SHA-256 checked while copying, before any request; they are never changed. `AllowNetwork = false` (default true) uses only the cache and local sources and raises `ModelAssetMissingException` for the files found in neither, before anything is copied.
- **Partial-download cleanup.** `RemovePartialDownloads(lock)` removes the lock's partial downloads and lock files under `.downloads/` (the store never removed lock files before), skipping a file whose lock another downloader holds. A downloader that is granted a lock file which was unlinked meanwhile takes the lock again by name. Returns `ModelCacheCleanup` (`Removed`, `Skipped`, `BytesRemoved`) of `ModelCacheEntry` values.
- **Cache pruning.** `PlanPrune(keepLocks)` lists, changing nothing, the snapshot directories no kept lock names and, under `.downloads/`, partial downloads that are not of a kept lock's file and lock files (`ModelCachePrunePlan`). `Prune(plan)` removes them, checking each lock again and skipping what is in use; `Prune(keepLocks)` does both. Only directories in the cache layout (`<owner>/<name>/<40-character SHA>`) are listed.
- **Lock format version 3.** `ModelAssetLock.DisplayName` and `ModelAssetLock.Hosting` (`ModelAssetHosting(repository, revision)`), with `HostingRepository` and `HostingRevision`: Hub-layout files are downloaded from the hosting repository and commit, while the cache directory and messages keep the lock's own `Repository` and `Revision`. JSON `display_name` and `hosting`; `ToJson` writes the lowest version that holds the lock, so existing locks still write version 1 or 2, and `Parse` reads 1 to 3. `ModelAssetLock.SchemaVersion` is 3 (was 2); new `SourcesSchemaVersion` (2).
- **Lock interchange.** The JSON lock is documented as the interchange format for locks with other tools. New `model-pipeline/schemas/asset-lock.schema.json` (versions 1 to 3) and `model-pipeline validate-lock <files>`; the examples in `model-pipeline/tests/data/asset-locks/` are validated by the schema and round-tripped byte for byte by the .NET tests.
- **Tool.** `Starlings.Acquisition.Tool` gains `status` and `clean`, and `--parallel`, `--mirror`, `--from`, `--offline` and `--lock-timeout`; download progress shows the lock totals.

### Guided decoding through ONNX Runtime GenAI guidance (backlog B1, #139; code path only)

All additive, opt-in and experimental. Unguided requests are unchanged: without a guidance option the decode loop calls GenAI as before, and no Stable profile's contract, capability status, gate, tolerance or `protected/` file changed.

- **`Starlings.Generation.OnnxGenAI`.** New `GenerationGuidance` (`JsonSchema`, `Lark`, `Regex`; `Kind`, `Data`) and `GenerationGuidanceKind`. `GenerationOptions.Guidance` and `GenAISequenceOptions.Guidance` pass it to `GeneratorParams.SetGuidance`, which ONNX Runtime GenAI 0.17.1 already exposes, with llguidance compiled into the CPU and CUDA linux-x64 natives. - **Fast-forward tokens.** `GenerationGuidance.WithFastForward(maxTokensPerStep)` turns on GenAI's forced tokens, so the grammar's fixed text is appended without a decode step per token. GenAI appends forced tokens without checking the sequence's maximum length, so the decode loop sizes the sequence for `MaxNewTokens` plus that bound. The context-length check counts the bound, and a step that appends more fails the request. Forced tokens are completion tokens: they are returned in order before the step's selected token and go through the same token limit (a completion is cut at `MaxNewTokens`), stop ids, detokenization and stop sequences. New `GenAISequence.GenerateNextTokens()` returns every token a step appended. Off by default.
- **`Starlings.Models.Qwen35`.** `Qwen35ChatOptions.Guidance` passes a constraint through. Without the files, as with the published bundle, these requests still fail with `NotSupportedException`, whose message now names the missing files. Also rejected: JSON with offered tools, guidance with `enable_thinking` or with log probabilities, and a required function that is not offered. New `Qwen35ChatClientOptions.GuidanceFastForward` (default false) builds the tool grammar with fast-forward tokens.
- **Capabilities.** New `Qwen35Capabilities.All` keys `guidance.json_schema`, `guidance.lark` and `guidance.regex`: experimental. `structured_output`, `extensions_ai.tool_mode.required` and `extensions_ai.structured_output` stay unsupported, because the published bundle's variant directories have neither guidance file.

On the real fp32x model on CPU with the two files added to a temporary copy of the variant directory (local, one machine): a regex, a JSON schema and the required tool-call grammar were followed, with and without fast-forward, and unguided greedy ids still equal the reference. ### CPU prefill in 1,024-token chunks above 1,024 prompt tokens (backlog B2)

- **`Starlings.Models.Qwen35`.** When `Qwen35ChatOptions.PrefillChunkTokens` is null, CPU now prefills in chunks of the new `Qwen35ChatOptions.DefaultCpuPrefillChunkTokens` (1,024): a prompt of at most 1,024 tokens is still prefilled in one call, and a longer one in 1,024-token chunks. This bounds the transient logits buffer that ONNX Runtime GenAI allocates for every prompt position (about 1 MB per token in fp32: 1.65 GB for 1,666 tokens, 8.14 GB at the 8,192-token context) to about 1 GB, and cancellation now takes effect between chunks of a long prompt. CUDA keeps 512-token chunks. `PrefillChunkTokens = int.MaxValue` restores the one-call prefill.
- **Fidelity.** On the fp32x CPU profile, 1,024-token chunks gave greedy ids and step-0 log-probabilities bit-identical to one call on the 22 development prompts (the 1,666-token prompt is the one that changes path) and on a 4,112-token long-context prompt. G1 and G2 passed on the 32 release prompts with the new setting, with the hosted full step-0 reference vectors. No tolerance, fixture or capability status changed. See `docs/evidence/cpu-prefill-chunking-2026-10-26/`.
- **Performance.** On a shared 4-vCPU host the 1,666-token prefill took a median 18.2 s in 1,024-token chunks against 20.1 s in one call (4 runs each), and the 4,112-token prefill 48.4 s against 62.0 s. G5 was not rerun; its `long-prefill` workload now runs in two chunks.
- **Benchmarks.** The C# harness records `prefill_chunk_tokens` 1,024 on CPU, and the matched Python runner (`bench_qwen35_matched.py`) appends the prompt in 1,024-token chunks on CPU by default, so G5 keeps comparing the same execution path.

  `TranscribeMelWithTimestamps` return a `WhisperTranscription` (text, `WhisperSegment` list with start and end in
  seconds, text and token ids, and the decoded `WhisperWindow`s); with #222 below, for audio of any length. `WhisperModel.GenerateWithTimestamps`
  applies transformers 5.18.0 `WhisperTimeStampLogitsProcessor`; the transcriber follows `generate(return_timestamps=True)`'s
  sequential seek loop, greedy, without fallbacks. Capability `timestamps` moves from unsupported to experimental; the new
  `word_timestamps` is unsupported.
- **Obsolete:** `WhisperCapabilities.StableProfile`, replaced by `WhisperCapabilities.CpuProfile` (same value; the profile is
  Experimental, not Stable). Removed in the next minor version.
- `WhisperTokenizer.Decode` drops timestamp tokens (ids from 50365), as transformers `WhisperTokenizer.decode` does.
- `WhisperOptions.NoTimestamps = false` now makes `Transcribe` return the timestamped decode's text, instead of
  prompting without `<|notimestamps|>` and decoding without the timestamp rules.
- **KV-cache decoding (experimental, #192), now the default.** `WhisperModelAssets.Lock` adds
  `onnx/decoder_with_past_model_fp16.onnx` (317,742,004 bytes, same revision), so `DownloadAsync` fetches about 318 MB
  more. **Upgrading:** a cache acquired before this change lacks that file, so `WhisperModelAssets.OpenLocal` and
  `OpenDirectory` throw `ModelAssetMissingException` until `WhisperModelAssets.DownloadAsync` runs again (it fetches only
  the missing file). This applies with `DecoderMode = FullContext` too: the lock is one set of files, and that mode
  merely does not load the graph. `WhisperModel` runs the full-context decoder once over the prompt and then one cached step per token;
  `WhisperOptions.DecoderMode = WhisperDecoderMode.FullContext` keeps the previous loop. Logits differ from the
  full-context loop in the last bits (fp16 summation order; bounded on the route), ids are equal. New:
  `WhisperDecoderMode`, `WhisperOptions.DecoderMode` and `DecoderWithPastSession`, `WhisperModelFiles.DecoderWithPastPath`,
  path overloads of `WhisperModel.Create` and `WhisperTranscriber.Create` with the KV-cache graph, and
  `WhisperModel.GenerateRecordingLogits` (diagnostics). Capability `kv_cache`: experimental.
- **Long-form transcription (experimental, #222).** `Transcribe` and `TranscribeWithTimestamps` accept clips
  of more than 3000 mel frames (480,160 samples or more; up to 480,159 samples stay one window, as in transformers) and
  transcribe them as transformers 5.18.0 sequential long-form `generate` does: the new
  `WhisperMelSpectrogram.ExtractLongForm` computes one spectrogram over the whole clip, and the timestamped decode walks
  it in 30 s windows, seeking to the last closing timestamp. `TranscribeMelWithTimestamps` takes a spectrogram of any
  number of frames. Greedy only; the temperature fallback, compression-ratio, log-probability and no-speech thresholds
  and conditioning on earlier windows stay unsupported (new capability keys say so). Capability `chunking` moves from
  unsupported to experimental. The Whisper route reads `asr-corpus-v3.jsonl`, which adds a 34.5 s and a 59.1 s
  composite of consecutive LibriSpeech utterances. `WhisperMelSpectrogram.ExtractLongForm` takes a `CancellationToken`
  (observed every 1024 frames); the spectrogram costs about 70 s of one core and about 1 GB per hour of audio.
- The Whisper onboarding route reads `asr-corpus-v2.jsonl`: the four clips of v1, a 27.9 s composite of six
  consecutive LibriSpeech utterances, and a composite cut at 30 s inside its last utterance (its decode ends inside a
  segment and is decoded again from the last closing timestamp). It checks the timestamped decode of every clip and
  that the corpus exercises a timestamp pair and that re-decode.

### Starlings.Runtime.Onnx: raw CUDA options, public validation, intervention diagnostics

- `OnnxCudaProviderOptions.AdditionalProviderOptions` passes further CUDA provider options as raw key-value strings, after the typed ones. Starlings rejects only a blank key, a null value, or a key that Starlings or a typed member sets (`device_id`, `use_tf32`, `gpu_mem_limit`, `arena_extend_strategy`, `cudnn_conv_algo_search`, `enable_cuda_graph`); ONNX Runtime rejects an unknown key or bad value when the provider is created, and the error then names the additional keys. The dictionary is copied when set. Untested on CUDA; no parity claim covers options set this way.
- `OnnxSessionOptions.Validate()` and `OnnxCudaProviderOptions.Validate()` are public: the checks of session creation, without a model or GPU.
- `OnnxInterventionDiagnostics` (experimental): the intervention identity of a session (original and loaded graph digests, `LoadedModelSha256Source`, profile ids, intervention inputs), built by a model package that loads a derived intervention graph. Design: `docs/interventions/architecture.md`. The intervention companions themselves (`Starlings.Interventions`, `Starlings.Models.Lfm3.Interventions`) are not published.

## Upgrading from 0.3.0

- Raise every `Starlings.*` reference to `0.4.0` together. The tokenizer comes along as `0.3.4`.
- Stable profiles produce the same outputs. One default changed: `EmbeddingGemma2ImageDecoder.Decode(Stream)` rejects more than 64 MiB of encoded input (`EmbeddingGemma2ImageTooLargeException`); raise `EmbeddingGemma2ImageDecoderOptions.MaxEncodedBytes` to keep decoding larger streams.
- `KevDecision[id]` with a null id throws `ArgumentNullException` (it threw `KeyNotFoundException`).
- `Starlings.Models.Lfm3` is new: read its `LICENSE.txt` before use. The LFM Open License v1.0 licenses commercial use only below USD 10 million annual revenue.
- `Starlings.Models.Bert`: add `Microsoft.ML.OnnxRuntime` 1.30.0 (the CPU natives) to the application. Pick a profile with `BertModelProfile.BuiltIn("bge-small")` (names in `BertModelProfile.BuiltInIds`) in place of `BertModelProfile.Load("model-pipeline/candidates/bge-small/profile.json")`. `Load` and `Parse` still work.
- If you used the BERT library from source before this release: `bge-m3`'s `RuntimeLock` now has **3 files** (`onnx/model.onnx`, `onnx/model.onnx_data`, `tokenizer.json`), not 2, because its graph keeps its weights in external data (#146). Download `RuntimeLock` again, or `Create` reports the missing `onnx/model.onnx_data`. `bge-reranker-v2-m3` has the same 3 files. The other five profiles still need 2.
- Reranker scores (ms-marco and bge-reranker-v2-m3) are raw logits, not probabilities. Apply a sigmoid yourself for bge-reranker-v2-m3's 0-1 mapping. nomic-embed-text-v1.5 vectors are not unit length.
- An executable or test project that references a Starlings model runtime package (not a definition package such as `Starlings.Models.Qwen35`, `Starlings.Models.QwenChat` or `Starlings.Models.Kev`) without a native package now gets warning `STARLINGS001` or `STARLINGS003` at build time (an error under `TreatWarningsAsErrors`). Add the native package, or set the opt-out property if the application deploys its own native library.
- A project with both a CPU and a GPU native package of one runtime now fails to build (`STARLINGS002`, `STARLINGS004`). Such a project shipped two copies of one native library, of which the loader picked one; keep one package.
- `Starlings.Models.Abstractions` breaks nothing: every former member is still there, marked `[Obsolete]`. Projects that treat warnings as errors see CS0618 until they move to the replacements above.
- A file that imports both `Starlings.Models` and `Starlings.Models.E5` sees two types named `CapabilityStatus` until the obsolete one is removed: qualify it or alias it (`using Status = Starlings.Models.CapabilityStatus;`).
- Code that tested for the exact type `ArgumentException` (not `is ArgumentException`) on an over-long e5 id sequence now gets `InputTooLongException`, a subclass.
- A class outside these packages that implements `ITextEmbedder` (new in this release) must also implement `CountTokens(text)`, `CountTokens(texts)` and `Validate(text)`.
- `KevInputTooLongException.Message` for an over-long question now starts with `question <index>:` and, when several questions are over a limit, names all of them. Code that matched the old message text needs the new form; the properties are unchanged.
- An `EmbeddingGemma2MultimodalOptions.Session.KnownModelSha256` is ignored: each of the three graphs takes its own digest from the files.
- Add `Starlings.Models.Abstractions` at the same version as the other `Starlings.*` packages; it comes in transitively with e5, EmbeddingGemma 2 and GLiNER2.
- `ModelAssetLock.SchemaVersion` is now 3. It is a constant, so code compiled against an earlier version keeps the old value until it is rebuilt; code that compared a lock's version with it should use `SourcesSchemaVersion` for version 2.
- An `IProgress<ModelAssetProgress>` that switched over `ModelAssetStage` sees the new value `Waiting`.
- An XML doc cref or a method group that named `ModelAssetStore.DownloadAsync` or `OpenLocal` without parameters is ambiguous now that both have a second overload; name the overload.
- Guided decoding breaks nothing: requests that set no guidance behave as before.
